# 毎日開かせるための GUI・仕組みアイデア(視点: 習慣化・行動科学)

対象: `/Users/yk/dev/guitar-diagnosis` ギター練習 PWA
作成: 2026-09-23

## 前提として読み取ったこと

- コアループ: スレッド(引っかかるフレーズ)を作る → 録音(テイク) → 直前 / ベスト / お手本と自動比較 → ばらつき(ms)・一致率 → 安定したら「解決済み」(自己確認 3 択つき)
- 制約: 完全クライアントサイド(IndexedDB / Dexie、バックエンド・アカウント無し)。正解データ無し。スコアは**正しさではなく一貫性**。
- 既存データ(`app/src/db.ts`): `threads(lastActivityAt, status, metronome)` / `takes(recordedAt, durationMs, metronome, gridTiming)` / `diagnosisResults(timingJitterMs, noteMatchRate, ...)` / `songThroughCompletions(at)`。「いつ・どのスレッドで・何本録ったか」は**すべて既存データから導出できる**。ユーザー設定(目標・表示 ON/OFF)を持つテーブルだけが無い。
- 画面: `ThreadList`(ホーム。アクティブ/曲通し/解決済み/デモ/バックアップが縦に並ぶ)→ `ThreadDetail`(メトロノーム設定・録音ボタン・推移グラフ・お手本・テイク履歴・解決ボタン)→ `DiagnosisView`。ルーター無し(`App.tsx` の判別ユニオン)。
- PRD の Non-goal に「利用を促す通知・リマインド機能(v1 では持たない)」がある。以下では**通知に頼らず、開いた瞬間と閉じる瞬間の体験で毎日を作る**ことを主軸にし、通知系は「ユーザーが自分で設定する」形だけを末尾に添える。
- ギター練習の文脈: 1 回 5〜15 分。両手が塞がる。毎日同じフレーズを弾く飽き。上達が日単位では見えない(ms 単位のばらつきは日々ノイズで上下する)。

行動科学の骨組み(Fogg の B=MAP): **トリガー(Prompt)** は通知無しなので「開いたときの一番上」と「前回閉じた直前の余韻」で代替する。**能力(Ability)** は録音までのタップ数と手の問題。**動機(Motivation)** は「見えない上達を見える形にする」「小さく積む」「失うと惜しい」。

## 1. 今日の 1 テイク

**一言説明**: ホームの最上部に「今日はこれを 1 本録ろう」というスレッドを 1 枚だけ大きく出し、そのカードのボタン 1 つで録音開始までいける。録ったら「今日の分は完了」に切り替わる。

**根拠**: 開いたときに「どのスレッドをやるか」を選ばせる時点で摩擦が生まれる(選択のパラドックス)。「1 本だけ」という最小行動(Tiny Habits / Minimum Viable Action)にすると、疲れた日でも開く理由が残る。1 本録ると多くの場合そのまま続ける(着手効果)。「完了」の状態変化が日次の小報酬になる。

**画面イメージ**: `ThreadList` の「アクティブなスレッド」見出しより上に hero カードを追加。
- 中身: スレッド名 / 「前回: 3 日前・ばらつき 42ms」 / 「● この 1 本を録る」(タップで `ThreadDetail` に遷移し、前回のメトロノーム設定のまま録音ボタンにフォーカス。または録音を即開始)
- 選び方(全部既存データ): (a) 今日まだ録っていないアクティブスレッドのうち `lastActivityAt` が最も古いもの、(b) ただし後述 5 の「解決まであと 1 テイク」があればそれを優先(目標勾配)、(c) アクティブが 0 なら「引っかかっているフレーズを 1 つ登録する」に化ける。
- 録音済みなら「✓ 今日の分は完了。もう 1 本?」+ 次候補。

**実装の当たり**: `db.takes.where('recordedAt').above(今日 0 時)` と `threads.where({status:'active'})` で決まる。`App.tsx` に「録音を即開始して開く」フラグを `Screen` に足す程度。新テーブル不要。

**コスト / リスク**: S。リスク: 毎日同じスレッドが出ると飽きる → 「別のにする」リンクを付ける。「今日の分は完了」が「もう十分」の合図になり 1 本で終わる人が増える可能性 → 完了後の文言は「もう 1 本?」寄りにする。

## 2. 練習カレンダー(週ごとの点)

**一言説明**: 直近 8〜12 週を「週 × 曜日」の点で描き、録音した日を塗る。連続日数ではなく「今週◯日 / 先週◯日」を主表示にする。

**根拠**: セルフモニタリング(記録するだけで行動が増える)と「鎖を切りたくない」損失回避。ただし厳密な日次ストリークは 1 日抜けた瞬間に全損して「どうでもよくなる(what-the-hell effect)」を起こすので、**週単位の点** + 「今週あと◯日で目標達成」に寄せる。ストリークを出す場合も「週 1 回まで休んでも途切れない」猶予(freeze)を入れる。

**画面イメージ**: `ThreadList` の hero(#1)直下に横長の小さなヒートマップ(7 列 × 8〜12 行、または 1 行 = 1 週で横スクロール)。セル濃度 = その日のテイク数(1 / 2〜3 / 4 以上)。曲通し完走も同じ日に点として数える。タップでその日に録ったスレッド一覧をポップ表示(過去を振り返る導線)。

**実装の当たり**: `takes.recordedAt`(`role:'normal'`, `sourceType !== 'demo'`)と `songThroughCompletions.at` を日付に丸めて集計するだけ。`useLiveQuery` 1 本。新テーブル不要。デモテイクは除外しないと「3 週間毎日やった」ように見えるので注意。

**コスト / リスク**: S〜M。逆効果になる条件: 空白が多いカレンダーを毎回見せると自己効力感を削る(特に再開時)。→ 直近 4 週だけ既定表示、空白期間は「◯日ぶり。おかえり」と前向きに書く(#4 と連動)。日次ストリーク数を大きく出さない。

## 3. 週◯日の約束

**一言説明**: 初回起動時(または設定から)「週に何日弾く?」を 2〜5 日から選ばせ、ホームにリング(今週 2/4)で出す。

**根拠**: 自分で宣言した目標は守りたくなる(コミットメント・一貫性)。目標に近づくほど加速する目標勾配効果(2/4 → 3/4 で「あと 1 日」)。毎日 100% ではなく達成可能な頻度を自分で決めることで、失敗時の全損感を避ける。

**画面イメージ**: `ThreadList` の topbar 直下に小さなリング「今週 3/4 日」。達成すると色が変わり「今週の約束を守った」1 行。未設定なら hero カード下に「週に何日弾く? [2][3][4][5][毎日]」のピル(既存の `pill-row` を流用)。

**実装の当たり**: ユーザー設定を持つ場所が無いので Dexie version 3 で `settings: 'key'` テーブル(key-value)を追加。`weeklyGoalDays` 1 件。週の境界は月曜固定でよい。集計は #2 と同じ。

**コスト / リスク**: S。リスク: 目標を高く設定しすぎて未達が続くと離脱。→ 未達 2 週連続で「目標を下げる?」を提案。「毎日」は選べるが既定は 3〜4 日。

## 4. 前回のつづきカード

**一言説明**: スレッドを開いた瞬間、前回の結論(何が良く何がズレたか)と、今日の一手を 1〜2 行で出す。3 日以上空いていたら「◯日ぶり。まず 1 本録って前回と比べよう」に切り替わる。

**根拠**: 再開時の最大の摩擦は「前どこまでやったか思い出す」コスト。PRD シナリオ 6 そのもの。空白期間の後の再開を「リセット」ではなく「続き」として扱うことで、フレッシュスタート効果を「やり直し」に向けさせる。

**画面イメージ**: `ThreadDetail` の録音ボタンの直上にカード:
- 「前回(9/20): ばらつき 38ms(その前 51ms)。後半 2 拍目がズレやすい」(`deviationTimeline` の severity 最大区間を言葉にする)
- 「今日の一手: 同じ ♩=80 で 1 本。安定したら ♩=85」(#9 と連動)
- 空白 7 日以上なら「1 週間ぶり。前回の感覚が残っているか、まず 1 本」。比較モードを `best` に自動提案(直前ではなくベストと比べると、久しぶりでも下がった感じが出にくい…と見せかけて、実際は上がり下がりが見えるので正直に出す)。

**実装の当たり**: `takes` 先頭 2 件と対応する `diagnosisResults`、`gridTiming` から生成。文言テンプレートは数種類の分岐。新テーブル不要。

**コスト / リスク**: S〜M。リスク: 機械的な要約が的外れだと信用を失う → 数値以外の言語化は控えめに(区間の位置を「前半 / 後半 / ◯拍目」まで)。

## 5. 解決までの距離

**一言説明**: スレッドごとに「解決の目安」(例: 直近 3 テイク連続でばらつき 30ms 以下、または音符一致率 90% 以上)を持ち、「あと 2 テイク」「あと 1 テイク」を出す。

**根拠**: 目標勾配効果。ゴールが見えると残りの努力が加速する。今は「解決済みにする」がユーザーの気分次第で、ゴール感が無い。「あと 1 テイク」はその日に開く強い理由になる。

**画面イメージ**: `ThreadDetail` 推移グラフの下に横バー「解決の目安まで ●●○(3 テイク中 2 本クリア)」。`ThreadList` のカードにも「あと 1 本」バッジ(#1 の hero 優先条件)。目安はスレッド作成時の既定値 + 手で変更可(ピルで「ゆるめ / 標準 / きびしめ」)。達成しても自動では解決にしない。「目安に達しました。自己確認 → 解決済み」ボタンに変わるだけ。

**実装の当たり**: `gridTiming.jitterMs`(メトロノーム有)か `diagnosisResults.timingJitterMs` / `noteMatchRate` を直近 N 件見るだけ。閾値は `Thread` に任意フィールド `resolveCriteria?` を足す(既存レコードは既定値扱いで、Dexie のバージョンアップは不要。インデックスに乗せない)。

**コスト / リスク**: M。リスク: スコアは一貫性であり正しさではない。ゆっくり弾けば安定するので、**tempoDiffPct / BPM が下がっていないこと**を条件に含めないと「遅く弾いて解決」を誘発する。達成条件の説明で「同じように弾けているか」の指標であることを毎回明記。

## 6. スレッドの「冷え」

**一言説明**: アクティブなスレッドのカードが、最後のテイクから日が経つほど視覚的に「冷えて」いく(色温度が下がる / 「3 日前」→「1 週間前」の文字)。録ると温まる。

**根拠**: 損失回避を「ストリーク」ではなく「自分の育てたスレッドの温度」に向ける。日次連続に比べて、1 つのスレッドをサボっても他が温かければ全損しない。「温め直す」行為が開く動機になる。PRD の「アクティブは少数に絞る」とも噛み合う(冷えたものが多いと絞りたくなる)。

**画面イメージ**: `ThreadList` カードの左端に細い縦バー(温→冷の 4 段階)と `meta` を「最終更新: 2026/9/20 …」から「3 日前 · 12 テイク」へ変える。冷えの最大段階でも赤や警告アイコンは使わず、グレーに落ちるだけ。14 日以上放置は「休眠」セクションに自動で畳む(選択肢を減らす = #1 の摩擦除去にも効く)。

**実装の当たり**: `lastActivityAt` のみ。CSS 変数 4 段階。新テーブル不要。

**コスト / リスク**: S。リスク: 罪悪感の演出になると開くのが嫌になる → 色は落とすだけ、文言は中立(「◯日前」)。休眠に畳む際は「解決済みにする / 削除 / 再開」を出して整理の機会にする。

## 7. 手を離さず録る

**一言説明**: (a) 録音ボタンを押した後、最初の音を検知して自動で解析開始点にし、無音が 3 秒続いたら自動停止 → そのまま診断へ。(b) ホーム画面アイコンの長押しショートカットやアプリ起動直後に「今日の 1 テイク」の録音画面へ直行。

**根拠**: Fogg の Ability。ギターを構えた状態で端末を触るのは物理的コストが高く、これが「今日はいいか」の言い訳になる。1 テイクあたりの端末操作を「録音ボタン 1 回」まで減らす。開始から録音まで 2 タップ以内に収めると習慣のループが短くなる。

**画面イメージ**: `ThreadDetail` の録音ボタンの隣に「自動停止」トグル(既定 ON)。録音中は「弾き終わって 3 秒静かにすると止まります」の 1 行と、無音カウントダウン(3・2・1)を count-in と同じ大きな数字で出す。メトロノーム有の場合は「◯小節で止める」を指定できる(拍数で確定)。manifest の `shortcuts` に「今日の 1 テイクを録る」(`start_url: './?quick=1'`)を追加し、`App.tsx` 起点で hero スレッドの `ThreadDetail` を開いて録音待機にする。

**実装の当たり**: 無音検知は既に `preprocess.ts` に RMS エンベロープの判定があるので、録音中に AnalyserNode で同じ閾値を回すだけ。手が塞がる問題の本命は自動停止。マニフェスト `shortcuts` は vite-plugin-pwa の manifest に配列を足す。新テーブル不要。

**コスト / リスク**: M。リスク: 自動停止が早すぎる(休符の長いフレーズ)→ 無音秒数をスレッド設定に。iOS Safari は manifest shortcuts 非対応(害は無い)。Web Speech で音声コマンドは誤動作と権限の割に効果が薄いので見送り。

## 8. 今日の発見カード

**一言説明**: 診断が終わるたびに、その日その人にだけ当てはまる「発見」を 1 枚出す(「1 週間前の自分より 15ms 安定」「このスレッドの過去ベスト」「初テイクから 21 日。音符の抜けが 6 → 2 個」「今日はテンポが 4% 速いのに一致率は同じ」)。

**根拠**: 可変報酬。毎回同じ数字(ばらつき ms)だと報酬が予測可能になり飽きる。日単位のノイズで数字が下がった日でも、比較軸(直前 / ベスト / 1 週間前 / 初回 / 同 BPM のテイク)を変えれば真実の「良い発見」が見つかることが多く、内容を変えられるからこそ可変になる。上達が見えにくい問題の直接対策。

**画面イメージ**: `DiagnosisView` の最上部(数値の前)に 1 枚カード。見出し 1 行 + 根拠 1 行 + 「くわしく」でグラフの該当点をハイライト。良い発見が無い日は、嘘をつかずに事実型の発見(「今週 4 本目。このスレッドで一番録った週」)に切り替える。同じ型が 3 回連続で出ないように型をローテーション。

**実装の当たり**: 発見の「型」を 8〜10 個関数で用意し、条件に合うものから 1 つ選ぶ(乱択 + 直近履歴で重み付け)。データは `takes` + `diagnosisResults` で足りる。表示したものを保存したいなら `settings` に直近の型 ID を持つ程度。

**コスト / リスク**: M。リスク: 無理に褒めると信用を失う(「正しさではなく一貫性」の注記と矛盾する)。→ 数値の裏付けが取れるものだけ。悪化した日は「発見: 前回より 12ms ばらついた。後半で遅れる区間が増えた」を同じ枠で出し、枠自体は必ず出る(可変なのは内容であって出現ではない)。

## 9. 今日のお題(変化球)

**一言説明**: 同じフレーズを録る前に、小さな変化を 1 つ提案する: 「♩=80 → 85 に上げる」「BPM を 10 下げてノーミスを狙う」「お手本と比較モードで」「目を閉じて弾く」「1 本目は指慣らし、2 本目を本番として録る」。BPM 階段(60 → 100 の目標を 5 刻みで塗る)も出す。

**根拠**: 飽きの正体は「同じ刺激の繰り返し」。適度な難度の変化(フロー / 望ましい困難)で毎回が少し違うゲームになる。BPM 階段は目標勾配 + 進捗の可視化(ばらつき ms よりも「◯ BPM で安定」の方が上達として実感しやすい)。

**画面イメージ**: `ThreadDetail` の録音ボタン直上(#4 のカードと同じ枠の 2 行目)に「今日のお題: ♩=85 で 1 本(前回 80 で 30ms を切った)」+ 「採用(メトロノームを 85 に)」ボタン。スレッドに「目標 BPM」を任意入力させ、推移グラフ横に BPM 階段(達成 BPM を塗る)を表示。

**実装の当たり**: `Thread.metronome` と `takes.metronome.bpm` / `gridTiming.jitterMs` から「この BPM で安定した」を判定。目標 BPM は `Thread` に任意フィールド `targetBpm?`。お題の型はメトロノーム有無で 4〜6 種。新テーブル不要。

**コスト / リスク**: S〜M。リスク: お題を毎回強制すると押しつけになる → 提案は 1 つ、無視して録れる。BPM 上げの提案が早すぎると失敗が続き離脱する → 「直近 3 本が閾値以下」でだけ上げる。

## 10. 週のふりかえり

**一言説明**: 週が変わって最初に開いたとき、先週 1 週間のまとめを 1 画面で見せる(録った日数・テイク数・触ったスレッド・最も伸びたスレッド・解決本数)。「今週の 1 本目を録る」で閉じる。

**根拠**: フレッシュスタート効果(週初めや月初は新しい習慣を始めやすい・区切りで再コミットしやすい)。日単位では見えない上達を週単位で束ねると見える。「先週 0 本」の週も「新しい週」として再スタートを演出できる。

**画面イメージ**: `ThreadList` を開いたとき、条件(週が変わっている & 先週または今週にテイクがある、または 2 週以上空いた再開)を満たすと hero より上に折りたたみ可能なカード。内容は 3〜4 行の事実 + 「今週の約束: 週 4 日(変更)」(#3)+ 「今週の 1 本目を録る」ボタン(#1 に飛ぶ)。1 度閉じたらその週は出さない。

**実装の当たり**: 集計は #2 と同じ。「閉じた週」を `settings` に 1 キー保存(無ければ `localStorage` でも可)。最も伸びたスレッドは、週内の最初と最後のテイクの `gridTiming.jitterMs`(または `timingJitterMs`)の差。

**コスト / リスク**: M。リスク: 先週が空だったときの文言。「先週は 0 本」を大きく出すと罪悪感 → 「新しい週。まず 1 本」に振る。

## 11. 解決済みの棚と再確認

**一言説明**: 解決済みスレッドを「棚」として見せる(解決までの日数・テイク数・最初と最後のばらつき)。さらに 2〜4 週間後に「まだ弾ける? 1 本だけ確認」で 1 テイク分の再確認を促し、崩れていたら再アクティブ化できる。

**根拠**: 達成の蓄積(endowed progress)は継続の強い燃料になるが、現状の解決済みは薄いグレーの一覧で「消えた」感がある。再確認は間隔反復(spaced repetition)で定着させると同時に、「今日録るものが無い日」にも開く理由を作る。既にクリアしたフレーズは成功体験が約束されているので、開くハードルが低い。

**画面イメージ**: `ThreadList` の解決済みセクションを「◯本解決」の見出しとカード(「21 日 / 14 テイク / 58 → 27ms」)に。ホームの hero(#1)の候補に「再確認: ◯◯(解決から 3 週)」を週 1 回まで混ぜる。再確認で崩れていたら「アクティブに戻す」。

**実装の当たり**: 解決までの統計は `takes` で導出。再確認タイミングは `lastActivityAt` からの経過日数で導出(任意で `Thread.recheckAt?`)。再確認の録音は通常テイクとして保存され、比較モードは `best` を既定に。新テーブル不要。

**コスト / リスク**: S(棚)〜M(再確認)。リスク: 解決済みが増えると再確認要求が多くなる → 1 日 1 件、週 1 回まで。崩れた結果ばかりだと「解決」の価値が下がる → 崩れは「忘却は普通。もう 1 本で戻ることが多い」と説明。

## 12. 自分で決めるリマインド(通知無しで成立する版)

**一言説明**: アプリから通知は送らない(PRD Non-goal)。代わりに、ユーザーが「いつ・何のあとに練習するか」を 1 行で決める(実装意図: 「夕食を片付けたら 1 本」)。それをホームに掲示し、希望者だけ (a) カレンダー予定(.ics)をダウンロード、(b) インストール済み PWA のアイコンにバッジ(今日未録音なら「1」)を付ける。

**根拠**: 実装意図(if-then プラン)は習慣形成の効果量が最も安定して大きい手法の 1 つで、通知よりも「既存の行動に接続する」方が定着する。バッジは邪魔をしない受動的トリガー(ホーム画面でギターの近くに端末があれば目に入る)。

**画面イメージ**: `ThreadList` 下部「練習の習慣」セクション: 「[夕食を片付けたら] に [1 本] 録る」テンプレート入力 → hero カード(#1)の下に小さく掲示。「カレンダーに毎日の予定として入れる(.ics)」ボタン、「アプリアイコンに未完了バッジを出す」トグル。

**実装の当たり**: `settings` に `intention` と `badgeEnabled`。`.ics` は文字列生成 + Blob ダウンロード(`RRULE:FREQ=DAILY`)。バッジは `navigator.setAppBadge(1)` / `clearAppBadge()` を `visibilitychange` と録音完了時に呼ぶ。**制約**: アプリを閉じた後は更新できないので「今日未録音のまま閉じた → 翌日もバッジ 1 のまま」で実質「録るまで消えない印」になる(それで十分)。Web Push / Notification Triggers は不要。Chromium / Safari(iOS 16.4+ ホーム画面追加時)で動く。

**コスト / リスク**: S。リスク: PRD の Non-goal と衝突する印象 → 「アプリは何も送らない。ユーザーが自分の環境に置く」設計であることを UI で明示し、既定はすべて OFF。バッジは消し忘れると常に「1」で慣れて無視される → 録音時に必ず消す、任意で「解決済みにしたら消す」なども不要。
