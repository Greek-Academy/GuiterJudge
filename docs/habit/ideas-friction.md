# 「毎日開いて練習してくれる」ための GUI・仕組みのアイデア(視点: 練習の実際と、開いてから録音するまでの摩擦)

対象: `/Users/yk/dev/guitar-diagnosis/app`(React 19 + Dexie、ルーター無し、5 画面)。
前提として押さえた現状:

- 起動は常に一覧(`App.tsx` の `useState<Screen>({ name: 'list' })`)。前回どのスレッドを開いていたかは覚えていない
- 録音までの最短経路は「一覧 → スレッドカード → ● 録音する → (マイク許可) → 弾く → ■ 録音停止 → 解析待ち → 診断画面」。停止後は診断画面に飛び、**もう 1 回録るには ← 戻る が要る**
- 一覧の下半分はデモデータ・バックアップ・開発用が占めていて、日常利用者向けの情報は上の数枚のカードだけ
- `Take.audioBlob` は保存しているが、**生の録音を再生する UI がどこにも無い**(`preview.ts` は音符列を発振器で鳴らすだけ)
- メトロノームは録音時の付属機能で単体では鳴らせない。チューナーは無い
- PWA マニフェストの `icons: []`。ホーム追加の誘導も無い
- 生徒モデル(ONNX、4 MB)は 10 秒の録音を Mac で 0.7 秒で解析するが、**既定はまだ Basic Pitch**(検証画面のラジオで端末ごとに切替、`engine.ts` の localStorage)。起動時ウォームアップ(`main.tsx`)も Basic Pitch 側だけ
- PRD Non-goal: 「利用を促す通知・リマインド機能」は v1 では持たない。以下は **アプリを開いた後の体験**で毎日開く理由を作る方向に絞る

---

## 1. 続きから始まる起動

- **一言説明**: 前回開いていたスレッドを覚えておき、次に起動したときはそのスレッドの録音ボタンが見える状態から始める。一覧には ← で戻る。
- **減らす摩擦**: ギターを構えた状態で「一覧をスクロールしてカードを探す」1 タップ + 視線移動。毎日同じフレーズを続ける人には、起動 → 録音が 1 タップになる。
- **画面イメージ**: 既存 `ThreadDetail` をそのまま初期画面にする。一覧に戻ったときは先頭に「続きから: 〈スレッド名〉 ● 録る」のヒーローカードを置く(案 2 と統合可)。
- **実装の当たり**: `App.tsx` の初期 `Screen` を `localStorage('lastScreen')` から復元し、`setScreen` をラップして保存。スレッドが削除・解決済みなら一覧に落とす。DB 変更なし。
- **想定コスト**: S。リスク: 複数スレッドを回す人には「毎回同じスレッドが開く」のが邪魔になり得る → 直近 24 時間以内に開いた場合だけ復元、それ以外は一覧、という条件にする。

## 2. 「今日の 3 つ」が先頭にあるホーム

- **一言説明**: 一覧の先頭に、練習履歴から自動で組んだ今日のメニュー(最大 3 件)を置く。各カードに ● ボタンがあり、押すとそのスレッドで即録音が始まる。
- **増やす価値**: 開いた瞬間に「何をやるか」が決まる。PRD Problem「何を練習すべきか設計できず、なんとなく弾いて終わる」への直接の答え。デモ/バックアップ/開発用は「設定・データ」画面に追い出し、ホームを練習者の画面にする。
- **メニューの組み方**(どれも既存データから引ける):
  1. **続ける**: `lastActivityAt` が最新のアクティブスレッド(昨日の続き)
  2. **掘り起こす**: アクティブなのに `lastActivityAt` が 7 日以上前のスレッド(放置)。「〈9 日〉触っていません」と日数を出す
  3. **崩れていないか確かめる**: 解決済みで 14 日以上経ったスレッド(案 9 と連動)
  4. 3 件に満たなければ「新しいフレーズを登録」カードで埋める
- **画面イメージ**: `ThreadList` 上部に新セクション「今日やること」。カードは `.card` に `● 録る` の小ボタン(`button.secondary` の幅 auto 版、テイク履歴の「▶ 採譜」と同じスタイル)を右端に。既存の「アクティブなスレッド」はその下に残す。
- **実装の当たり**: `ThreadList.tsx` に `useLiveQuery` を 1 本追加して threads + takes から選ぶ(新テーブル不要)。「設定・データ」は `App.tsx` の `Screen` に `{ name: 'settings' }` を足して、デモ/バックアップ/開発用ボタンを新 `screens/Settings.tsx` に移す。
- **想定コスト**: M。リスク: スレッド数が 1〜2 の初期ユーザーではメニューが空に近い → 空のときは既存の空状態文言を出す。

## 3. カードから 1 タップで録音(録音の前倒し)

- **一言説明**: 一覧のカードやメニューの ● を押すと、スレッド詳細を開くのと同時に録音(メトロノーム設定があればカウントイン)が始まる。
- **減らす摩擦**: 「カードを開く → 画面下の録音ボタンまで視線を落として押す」の 2 動作が 1 動作に。右手にピックを持った状態で押すタップ数が半分になる。
- **画面イメージ**: `ThreadDetail` は既存のまま。開いた直後に録音中状態(カウントインの大きな数字)になる。録音ボタンは画面の**最上部**(トップバー直下)に上げ、メトロノーム設定パネルは折りたたみ(「♩=80 16分 4拍 ▾」の 1 行要約)にする。
- **実装の当たり**: `App.tsx` の `Screen` に `{ name: 'thread'; threadId; autoRecord?: true }` を足し、`ThreadDetail` に `autoRecord` prop を渡して `useEffect` で `handleRecordToggle()` を呼ぶ。`thread.metronome` の読込(`metroLoaded`)を待ってから開始する必要がある。`actions.startRecording` はそのまま使える。
- **想定コスト**: S。リスク: 初回はマイク許可ダイアログが出るので「開いたら勝手に録音」に見えないよう、許可未取得時はボタンを押させる(`navigator.permissions.query({name:'microphone'})` で判定、非対応ブラウザは従来どおり)。

## 4. ハンズフリー録音(音で始まり、静けさで終わる/小節数で終わる)

- **一言説明**: 録音を「待機」状態にしておくと、弾き始めの音で本番録音が始まり、演奏後の無音が続くか、指定した小節数を弾き終えると自動で停止して解析に入る。
- **減らす摩擦**: **■ 停止を押すために右手をギターから離す**という、このアプリで最も不自然な動作を無くす。停止のためのタップで最後の音が短く切れる問題も消える。
- **画面イメージ**: `ThreadDetail` の録音ボタンを「● 録る」→ 待機中「弾き始めてください…」(マイクレベルのバー付き)→ 録音中「録音中 … 止めると 2 秒で終了」→ 自動停止。メトロノーム ON のときは「小節数」ピル(2 / 4 / 8 / 手動)を `metro-panel` に足し、`countInBeats + beatsPerBar × 小節数` 拍で自動停止。
- **実装の当たり**: `recording.ts` の `Recorder` に `AnalyserNode`(または `ScriptProcessor`/`AudioWorklet`)を足し、RMS を 50ms ごとに監視するコールバックを付ける。開始トリガは `preprocess.ts` の無音判定と同じ考え方(ピーク比 + 絶対下限)。停止条件は `ThreadDetail` 側で判定して `stopRecordingAndDiagnose` を呼ぶ。小節数停止は `Metronome.onBeat` の `index` を数えるだけ。`MetronomeSpec` に `bars?: number` を足す(スレッドの既定値として保存、`db.ts` の型追加のみ、スキーマ変更不要)。
- **想定コスト**: M。リスク: 休符の長いフレーズで途中停止する → 無音しきい値は 2〜3 秒、メトロノーム時は小節数優先。部屋の暖房音などで開始トリガが誤発火 → 待機画面にレベルメーターを見せてしきい値を自分で確認できるようにする。
- **補足(S)**: `keydown` で Space/Enter を録音トグルに割り当てる。Bluetooth の譜めくりペダル(PageTurner 等)はキーボードとして見えるので、足で開始・停止できる。

## 5. 診断直後の「もう 1 回」ループ

- **一言説明**: 診断画面の下に固定バー「● もう 1 回録る」「一覧へ」を置く。同じメトロノーム設定で即座に次のテイクへ。今日そのスレッドで何テイク目かも表示。
- **減らす摩擦**: 現状は診断 → ← 戻る → スクロール → ● 録音する、の 3 動作。フレーズ練習は「弾く → 確認 → すぐ弾き直す」の反復が本体なので、この 1 往復が毎回のコスト。生徒モデルなら停止から診断表示まで 1 秒以内なので、ループが「止める → 数字を見る → 押す → 弾く」で回る。
- **画面イメージ**: `DiagnosisView` の最下部に `position: sticky; bottom: 0` のバー(`button.primary` 幅 auto ×2)。バーの上に「今日 3 テイク目 / ばらつき 24 → 19 → 17ms」のミニ推移(直近 3 テイクの値を矢印で並べるだけ)。
- **実装の当たり**: `App.tsx` に `onRecordAgain` を渡し、案 3 の `autoRecord: true` でスレッド画面へ遷移する。ミニ推移は `db.takes.where({threadId})` の今日分(`recordedAt >= 今日 0 時`)から `gridTiming.jitterMs` / 診断の `timingJitterMs` を並べる。DB 変更なし。
- **想定コスト**: S。リスク: 連続録音で `AudioContext` の数が増えないか確認(`recording.ts`/`metronome.ts` は共有コンテキスト化済みなので問題は小さい)。

## 6. 生の録音を聴く・過去の自分と聴き比べる(ビフォーアフター)

- **一言説明**: 保存している `audioBlob` をそのまま再生できるようにし、「1 週間前」「1 か月前」「最初のテイク」との A/B 切替再生を診断画面に置く。
- **増やす価値**: 数字(ばらつき ms)より先に、**耳で上達を実感する**。PRD Goal 1「伸びているかを実感できる」に一番直接的。今は発振器のプレビュー音しか聴けず、練習の記録としての「音」が死蔵されている。
- **画面イメージ**: `ThreadDetail` のテイクカードに「▶ 録音」(生音)を追加し、既存「▶ 採譜」と並べる。`DiagnosisView` に新セクション「聴き比べ」: 左右 2 つのボタン「▶ 今回」「▶ 〈9/16〉のテイク」と、比較相手を選ぶピル(1 週間前 / 1 か月前 / 最初 / 最良)。再生中は既存のピアノロールに再生位置の縦線を出す(`analysisOffsetMs` で時間軸を合わせる)。
- **実装の当たり**: `preview.ts` に `playBlob(blob): { stop, onTime }` を足す(`URL.createObjectURL` + `<audio>`、または `decodeAudioBlob` → `AudioBufferSourceNode`。後者なら既存の共有コンテキストが使え、再生位置も `ctx.currentTime` で取れる)。比較相手の選択は `takes.recordedAt` から「7 日前に最も近いテイク」を選ぶだけ。`PianoRoll.tsx` に `cursorMs?: number` prop を足す。
- **想定コスト**: M。リスク: iOS Safari の MediaRecorder は `audio/mp4` を吐くが `recording.ts` は Blob type を `audio/webm` 決め打ちで作っている → `recorder.mimeType` を Blob に使うよう直す(既存データは type 不一致でも `decodeAudioData` は中身で判定するので概ね再生できる)。エクスポート JSON が音声込みで大きい問題は既存のまま。

## 7. セッションの締め(今日のまとめカード)

- **一言説明**: 録音した日に一覧へ戻ると、先頭に「今日のまとめ」カードが出る。テイク数、触ったスレッド、一番良くなった指標、連続練習日数。「今日はここまで」ボタンで畳む。
- **増やす価値**: 練習の終わりに小さな達成感を出し、「明日も開く」動機にする。今は録音を終えても何も締まらず、診断の数字を見て閉じるだけ。
- **画面イメージ**: `ThreadList` 最上部(案 2 の「今日やること」の上、または録音があった日はそれに置き換わる)。`.stat-hero` 風に「今日 7 テイク / 2 スレッド / 連続 4 日」、下に「16 分のオルタネイト: ばらつき 31 → 22ms」の 1 行を最大 3 本。
- **実装の当たり**: `db.takes.where('recordedAt').above(今日 0 時)` と `songThroughCompletions.where('at').above(...)` の集計だけ。連続日数は `takes` の `recordedAt` を日付に丸めて数える(新テーブル不要。テイク数が数千になれば `Thread` にキャッシュを持つ)。「畳んだ」フラグは `localStorage('summaryDismissed:YYYY-MM-DD')`。
- **想定コスト**: S〜M。リスク: 「良くなった」の判定はばらつき ms の減少で出すが、`RELATIVE_JITTER_METRIC` の `flatThreshold`(4ms)未満は「横ばい」と言い切る既存方針を守る(小さな揺れを改善に見せない)。

## 8. 練習カレンダー(連続日数と穴が見える 4 週間の帯)

- **一言説明**: ホームの上部に直近 28 日のドット帯。録音した日(曲通しの完走も含む)に点が付き、今日と連続日数を強調する。タップするとその日のテイク一覧。
- **増やす価値**: 通知を持たない v1 で、**開いたときに「昨日空けた」と自分で気付ける**唯一の仕組み。PRD Success Metric「週 1 回以上の練習ログ継続率」をユーザー自身に見せることにもなる。
- **画面イメージ**: `ThreadList` のトップバー直下に高さ 28px 程度の 7 列 × 4 行のドット(SVG か flex)。右端に「連続 4 日」。`ScoreTrend.tsx` と同様に色は CSS 変数と同値のリテラルで持つ(SVG の `fill` に `var()` が効かない環境への既存対策に合わせる)。
- **実装の当たり**: `takes.recordedAt`(`role: 'normal'`, `sourceType !== 'demo'`)と `songThroughCompletions.at` を日付に丸めて Set にする `useLiveQuery` 1 本。新規 `components/PracticeCalendar.tsx`。DB 変更なし。
- **想定コスト**: S。リスク: デモデータのテイクを数えると偽の連続日数になる → `sourceType: 'demo'` を除外。

## 9. 解決済みの「崩れていないか」再確認と、放置スレッドの掘り起こし

- **一言説明**: 解決済みスレッドを開けるようにし、N 日おきに 1 テイクだけ「確認録音」を促す。ばらつきが解決時より明らかに悪化していたら「再開する」で active に戻せる。放置スレッドは案 2 のメニューで浮上させる。
- **増やす価値**: 「解決したフレーズは本当に定着しているか」は独学者が一番確認しにくい点。解決済みを死蔵せず**維持の練習**に変える。メニューの弾数(案 2)も増える。
- **画面イメージ**: `ThreadList` の解決済みカードを `onClick` 可能にし(今は `cursor: default` で押せない)、`ThreadDetail` に解決済み用のヘッダー「解決から 21 日。1 テイク録って崩れていないか確かめる」+ ● ボタン。診断後、解決時の最終テイクと比較して悪化していれば「再開する」ボタン(自己確認ステップの逆)。
- **実装の当たり**: `Thread` に `resolvedAt?: number` を足す(`db.ts` 型追加のみ、Dexie はスキーマ変更なしで OK。既存の解決済みは `lastActivityAt` で代用)。`actions.ts` に `reopenThread(threadId)`(`status: 'active'`)。比較は `recomputeDiagnosis` を `prev` で使い、解決時テイクは `resolvedSelfCheck` の付いた `DiagnosisResult.takeId` から引ける。
- **想定コスト**: S〜M。リスク: 「解決済み」の重みが軽くなる → 確認録音は既定 2 週間おき、メニューの 3 件目にしか出さない。

## 10. 道具箱を入口にする(単体メトロノーム + チューナー)

- **一言説明**: ホーム最上段に「チューナー」「メトロノーム」の 2 ボタン。練習の最初に必ずやる**チューニングとテンポ確認**をこのアプリで済ませると、その流れで「今日やること」が目に入る。
- **増やす価値**: 毎日開く理由を「診断したい日」から「ギターを持った日すべて」に広げる。チューニング → そのまま隣のスレッドで録音、が同じ画面内で完結する。
- **画面イメージ**: `ThreadList` トップバー直下に横並び 2 ボタン(`.pill-row` 流用)。メトロノームはボトムシート風のパネルで ♩ ステッパー(既存 `.metro-row` / `.stepper` を再利用)と ▶/■。チューナーは新画面 `screens/Tuner.tsx`: 検出音名を大きく(`.count-in .num` のサイズ感)、下にセント偏差の針、6 弦の目標音(E2 A2 D3 G3 B3 E4)を `.pill` で並べる。
- **実装の当たり**: メトロノームは `metronome.ts` の `Metronome` をそのまま使う(`countInBeats: 0`)。チューナーは Basic Pitch/生徒モデルでは重すぎるので、`getUserMedia` + `AnalyserNode.getFloatTimeDomainData` に自前の自己相関(YIN 簡略版、100 行程度)を書く。単音・持続音なので十分。`pitchNames.ts` の `pitchToName` を流用。
- **想定コスト**: M(メトロノーム単体は S、チューナーが M)。リスク: 低音弦(E2 = 82Hz)の自己相関は窓長が要る(4096 サンプル以上)。ハウリング防止でチューナー中はメトロノームを止める。

## 11. ホーム画面に追加の誘導とアイコン

- **一言説明**: PWA としてホーム画面に置かれるように、アイコンを用意し、数回使ったユーザーに画面内バナーで「ホーム画面に追加」を案内する(Android は `beforeinstallprompt`、iOS は共有シートの手順図)。
- **減らす摩擦**: 「ブラウザを開いて URL/ブックマークを探す」を無くす。毎日使うアプリは**アイコンが目に入ること自体がリマインダー**になり、PRD が禁じる通知に頼らずに済む。スタンドアロン表示なら URL バーも消えて録音ボタンが近くなる。
- **画面イメージ**: `ThreadList` の `notice`(既存の `.notice` スタイル)に「ホーム画面に追加すると 1 タップで開けます [追加する] [あとで]」。iOS では「共有 → ホーム画面に追加」の 2 行説明。`display-mode: standalone` のときは出さない。
- **実装の当たり**: `vite.config.ts` の `manifest.icons` を埋める(`public/icons.svg` はあるが PNG 192/512 が要る)。`beforeinstallprompt` を `main.tsx` で捕まえて保持し、`ThreadList` から `prompt()`。表示条件は `localStorage` のテイク数カウンタ(3 テイク以上、既に閉じていない)。
- **想定コスト**: S。リスク: iOS は自動誘導できないので手順説明にとどまる。`.phone` の 420px 固定枠はスマホ全画面だと余白が出る → `@media (max-width: 480px)` で `margin: 0; border-radius: 0; min-height: 100dvh` にする(これはどの案でも先にやる価値がある)。

## 12. 「待ち時間ゼロ」の見せ方(生徒モデルを既定にし、停止直後に結果)

- **一言説明**: 生徒モデルを既定エンジンにして起動時に読み込んでおき、■ 停止 → 診断表示を 1 秒以内に収める。ボタン文言の「処理中...」を「解析中 0.7 秒」の進捗バーに置き換え、テイク履歴と診断に「解析 0.7 秒」を出す。
- **減らす摩擦**: 停止後の**無言の待ち**(Basic Pitch は初回 8 秒、以後数百 ms〜数秒)。待ちが 1 秒未満なら案 5 のループが成立し、「録るのが面倒」という感覚が消える。速さは毎日使う理由になる。
- **画面イメージ**: `ThreadDetail` の録音ボタンが停止後 `.progress-track` に変わり、`timings` の実測でアニメーション。`DiagnosisView` の右上に小さく「生徒モデル / 0.7 秒」。既存の検証画面のラジオは「設定・データ」画面へ移す。
- **実装の当たり**: `engine.ts` の既定を `'student'` に変え(`localStorage` に `'basic-pitch'` を明示保存した端末だけ従来)、`main.tsx` の `scheduleIdle` で `preloadStudentModel()` も呼ぶ(`studentTranscribe.ts`)。`transcribe()` は既に `engine` と `timings` を返しているので、`Take` に `engine?: string` と `inferenceMs?: number` を足せば履歴に出せる(`db.ts` 型追加のみ)。
- **想定コスト**: S。リスク: **スマホ実測が未了**(Mac 0.7 秒の 2〜4 倍見込み、`FINETUNE_NOTES.md` 18 節)。初回の ONNX 読込(4 MB + WASM 14 MB、SW でキャッシュ済み)が遅い端末では 1 回目だけ待つ。ヘッドレスでは F1 90.2 / 87.9 だが自分の録音環境では未確認なので、切替直後は検証画面で目視する。

## 13. 曲通しをタイマーと録音で(手入力を無くす)

- **一言説明**: 曲通し画面の「今回も通しで弾いた +」を「▶ 通し開始」→ 経過タイマー → 「■ 完走」に置き換え、所要時間を自動で埋める。任意で音声も残す(診断はしない)。
- **減らす摩擦**: 弾き終わってからストップウォッチの値を思い出して数字を打つ、という作業を消す。曲通しは毎日の練習の締めになりやすいので、ここが楽だと開く回数が増える。
- **画面イメージ**: `SongThroughView` の先頭ボタンが `▶ 通し開始` → 大きな経過時間(`.count-in .num` 流用)+ `■ 完走` / `やめる` → 完走ログに追加。ログ行に「▶」が付き、案 6 の生音再生で聴き返せる。
- **実装の当たり**: `useState` のタイマーと `addSongThroughCompletion(threadId, elapsedSec)`。録音も残す場合は `Recorder` で録って `Take`(`role: 'normal'`, `noteEvents` 無し)として保存するか、`SongThroughCompletion` に `audioBlob?: Blob` を足す(後者が単純。型追加のみ)。
- **想定コスト**: S。リスク: 4 分の音声を毎回保存すると IndexedDB が膨らむ → 録音は任意トグル、既定 OFF。
