# 比較ロジックのテンポ事前正規化(P3、2026-09-23)

`app/src/comparison.ts` の `alignForDiagnosis()` に、アライメント前にテイクのテンポを揃える段を入れた。
背景は `musicxml-design.md` 4.1 と `results-summary.md` 4 節: 格子どおりのお手本(楽譜由来)と模擬演奏を比べると、
テンポが 5% 違うだけで 2 パス直線フィットの 1 パス目が崩れて回復しなかった。

## アルゴリズムの変更点

従来: 分割統合 → 仮アライメント(Needleman–Wunsch、挿入削除 6、時刻差 100ms あたり 1)→ 対応の開始時刻に直線 `take = a + b·ref` を最小二乗で当てる →
`(take − a) / b` の時間軸で再アライメント → 残差からジッタ等を算出。

変更後:

1. 分割統合後の両音符列から**テンポ比の候補**を作る。テイク全体の長さ(最初の音〜最後の音)の比 `span(take) / span(ref)` を、
   端から k = 0, 1, 2 音目どうしで測った 3 通り(両端の余分な音・弾き忘れ 1〜2 音に耐えるため)。各候補は k 音目の時刻をアンカーにして
   `take' = (take − anchorTake) / scale + anchorRef` に写す。比は 0.4〜2.5 に制限、どちらかが 4 音未満か 1 秒未満なら候補を出さない。
2. 「正規化なし(従来どおり)」を含む各候補について従来の 2 パスをそのまま回し、**2 パス目のアライメント総コスト**
   (対応: 音高差 + 残差/100、非対応: 6)が最小の候補を採る。同点なら正規化なし。
   対応数の最大化にしなかったのは、残差の大きい対応を 1 つ増やすだけの候補が勝ってしまうため(和音ありの jitter25 で 65 → 66 対応、ジッタ 25 → 69ms になった)。
3. 採用候補の直線 `take' = a + b·ref` を元の時刻に合成し直して `fit`(`take = A + B·ref`)として返す。`DiagnosisView` のピアノロールなど `fit` の利用側は無変更。
   `tempoDiffPct` は `B` から出るので正規化倍率込みの「真のテンポ差」になる。`tempoScale`(採用倍率、1 = なし)を `DiagnosisMetrics` / `DiagnosisResult`(任意)に足した。
4. **`tempoDiffPct` の符号を直した**。`B` は「今回の所要時間 / 基準の所要時間」なので、テンポ比は `1/B`。従来は `B − 1` を返していて、
   コメント・SPEC・`habit/verdict.ts`(`tempoDiffPct < −8` を「遅く弾いた」と判定)の「正 = 今回が速い」と逆だった。
   テンポ差が数%を超えると推定自体が 0% 付近に張り付いていたので表面化していなかったが、正規化で推定が正確になると
   遅く弾いたテイクが「+25%」と出て verdict も誤判定するため、ここで直した。以下の表の「旧」列は比較のため符号を反転して載せている。

テンポ差が小さい場合、候補どうしの 1 パス目の対応は同じになり、最小二乗の直線フィットは線形変換に不変なので、結果は従来と一致する(下の回帰確認)。

計算量: 候補 ≤ 4 × 2 パス = 最大 8 回の NW(従来 2 回)。60 秒・350 音でも Node で 1 曲あたり数十 ms。

## 既存の比較(人間 vs 人間、テンポ差小)への影響

### 実録音: GAPS test 30 曲(先頭 60 秒、`proto/gaps-regress.ts`)

同じ演奏の 3 つの採譜 — 正解 MIDI(gt)、公開モデルの採譜(hfmt、`~/dev/guitar/data/eval/results/hfmt-gaps-60s-test`)、
蒸留モデルの採譜(student、`student-final-60s-test`)— を「別テイク」と見なして `diagnose()` に通した。テンポ差 0、採譜誤差だけが違う 90 組。

| 条件 | 変化した組 | 対応数の差(平均 / 最大) | ジッタの差 ms(平均 / 最大) |
|---|---|---|---|
| 同じ時間軸(student の無音トリム量 `analysisOffsetMs` を足し戻して gt に揃える。**アプリの prev 比較に相当**: 両テイクともトリム後) | **7 / 90** | 0 / 1 | +0.1 / 5.7 |
| student を保存のまま(トリム後の時間軸。gt との間に一定オフセット 40ms〜14 秒、中央値 2.5 秒) | 59 / 90 | +33 / +137 | −115 / −387 |

1 行目が回帰確認: 変化した 7 組も対応数 ±1、ジッタ ±0.5ms(1 組だけ 222_W41wc gt→hfmt で 56.0 → 61.7ms、対応 239 → 240)で、実質同一。
2 行目は大きな一定オフセットのストレステストで、旧実装が一致率 0.2〜0.4・ジッタ 250〜380ms に崩れていた 58 組が、
新実装ではアンカー付き候補でオフセットが吸収されて一致率 0.8〜1.0・ジッタ 5〜130ms(gt→hfmt と同水準)になった。
アプリでは両テイクとも無音トリム後なのでこの状況は起きにくいが、お手本を「録音の途中から」弾き始めたような場合に効く。

### 合成テイク: `app/src/demo/` のデモ 5 スレッド(`proto/demo-regress.ts`)

`seed.ts` と同じフレーズ・崩れ方プロファイル・乱数シードで `performPhrase()` した音符列(音声合成 → 採譜は通していない)を prev で連鎖比較。
17 組すべて旧新で完全一致(対応数・ジッタ・弾き忘れ+余分が同値。`tempoDiffPct` は符号が反転するだけ)。

同じフレーズを bpm ×0.9(−10%)/ ×0.75(−25%)で弾いたテイクを追加すると:

## 実装メモ

- `alignForDiagnosis()` は純関数のまま。`DiagnosisAlignment.tempoScale`、`DiagnosisMetrics.tempoScale` を追加、`DiagnosisResult.tempoScale?` は任意。
- 保存済みの診断は作り直さない(Dexie の version は上げない)。`recomputeDiagnosis`(モード切替)や次の録音から新ロジックになる。
  `tempoDiffPct` の符号が古い診断と新しい診断で逆なので、スコア推移などで過去の値と並べる場合は注意(現状はジッタのみを推移に出しているので影響なし)。
- 模擬スクリプトと回帰スクリプトは scratchpad(`score-import/proto/sim2.ts`、`gaps-regress.ts`、`demo-regress.ts`)にあり、リポジトリには入れていない。
  `cmp-old/` に変更前の `comparison.ts` のコピー、`cmp/` に変更後のコピー(import に `.ts` を付けただけ)を置いて Node 24 で直接実行した。
