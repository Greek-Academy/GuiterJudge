# ギター上達診断アプリ 上流プラン(ロードマップ案、2026-09-23 時点)

対象期間: 2026-09 下旬〜2027-03(3〜6 か月)。根拠: PRD(docs/prd/)、Design Doc(docs/prd/、2 節、Appendix A / C)、SPEC(2・10・11・13 節)、MIDTERM_NOTES(docs/midterm/)、DEMO(5・6 節)、FINETUNE_NOTES(11〜20 節)、docs/habit/competition-result.md、docs/score-import/*、git log。
工数の数字はすべて**推測**(1 人日 = 集中作業 6 時間程度)。精度の数字は FINETUNE_NOTES / SPEC の実測値。

## 1. 現状の総括

### できていること(実装済みで数字の裏付けがあるもの)
- **コアループ**: スレッド、録音(マイク・音声・動画)、音符起こし、アライメント(2 パス直線フィット + テンポ事前正規化)、単位付きの指標、推移グラフ、解決時の自己確認。すべて端末内で完結。
- **お手本の入口 B / C / D**: 講師録音、既存テイクの昇格、MusicXML / .mxl。MusicXML は GAPS 404 曲で例外 0、MuseScore MIDI との一致 87〜99%。
- **和音はコード進行として診断**: GuitarSet ストローク系でルート 84〜93%(ジャズ・ファンク 51〜64%)。
- **生徒モデル v3(4.1 MB ONNX)**: 本番経路で GAPS F1 90.8 / GuitarSet 88.9(Basic Pitch 80.2 / 81.3、教師 94.7 / 90.4)。Mac ヘッドレス Chrome 1 スレッドで 10 秒の録音に 0.7 秒。
- **毎日の型**: 6 案(C01 / C02 / C03 / C07 / C11 / C13)。Dexie version は据え置き、状態は派生値と localStorage 2 キー。
- **評価の仕組み**: GAPS / GuitarSet を本番の `transcribe()` に通す採点と、蒸留パイプライン。

### 仮説のまま検証していないこと
1. **スマホで動くか、速いか**。推論時間、メモリ、34 MB プリキャッシュの初回ダウンロード、iOS Safari の録音、ホーム追加。実機計測はゼロ。
2. **自分の録音環境での精度**。GAPS / GuitarSet は他人のスタジオ品質録音。
3. **同じように弾いたときの指標の揺れ(ノイズの底)**。habit の勝敗しきい値(4ms、5pt)とゲージ −1 条件(12ms)は未較正。ノイズがしきい値より大きければ勝敗は乱数になる。
4. **Design Doc 8 節の M1 成功基準が未達**(主観の良し悪しと指標の上下が一致するか)。
5. **PRD Goal 1(伸びと停滞を実感できる)と主要指標(4 週間の週 1 回以上継続率)**。自分以外のユーザーはゼロ。
6. **生徒モデルで守備範囲が広がるか**(ストロークの音符単位、約 178ms 間隔の速いパッセージ)。
7. **スレッドの粒度、アクティブ数の上限**(PRD Open Questions)。

### 技術的負債
- SPEC の 3 節(技術スタック)・11 節・2 節が Basic Pitch 前提のまま、冒頭の対象時点も 09-02。
- 録音 Blob を `audio/webm` に決め打ち(`app/src/recording.ts`)。iOS Safari は mp4 を出すので再生・聴き比べで壊れる恐れ。
- manifest の `icons: []`(Android でインストール可能と判定されない可能性、要確認)。
- プリキャッシュ 34 MB(ORT WASM 14 MB、両エンジンを常時保持)。
- ORT は `numThreads = 1` 固定(マルチスレッドには COOP/COEP が要る)。
- テストが `src/score/` にしか無い(`comparison.ts`、`habit/verdict.ts`、`pickToday.ts` は純関数なのに未テスト)。
- リモート推論(CORS 全許可・認証なし)が URL 設定で最優先になる。配布版での扱い未決。
- 比較ロジックはルバートに弱い(事前正規化は一定のテンポ差にしか効かない)。
- 蒸留の validation 指標がぶれ、test と連動しない。
- スレッドの削除・編集ができない。

## 3. ロードマップ

### フェーズ 0: 実機で自分が使う(09 下旬〜10 月上旬、2 週間)
- **目的**: Q1・Q2 に答え、自分が毎日使える状態にする。
- **タスク**: https での静的ホスティング(D5)、manifest アイコンとスマホ幅 CSS、Vite の `base`。録音 `mimeType` を `isTypeSupported` で選ぶ(Android Chrome は webm/opus なので現状でも動く見込み。iOS 対策として先に入れておく)。段階別 ms の計測表示と端末内保存・JSON エクスポート。Q1 / Q2 の計測。既定エンジンの決定(D1)と Basic Pitch の遅延読み込み化。SPEC の更新。
- **完了条件**: 開発者の Android 端末で 10 秒の録音から 3 秒以内に診断(iOS は未確認のまま進み、フェーズ 2 初日に参加者端末で確認)。自分が 10 日以上・50 テイク以上。ノイズの底の表が docs にある。
- **工数**: 開発 4〜6 人日、計測・自己使用 毎日 15 分。
- **依存**: D5、実機。

### フェーズ 1: 指標の較正とベータ準備(10 月中旬、1〜2 週間)
- **タスク**: ノイズの底からしきい値を決め直す(例: 同じ演奏での Δ の 80 パーセンタイル)、`verdict.ts` / `comparison.ts` のテスト。自己採点 UI(実験フラグ)と端末内ログ。オンボーディング 3 画面、スレッドの削除・名前変更。案内・同意書・アンケート。
- **完了条件**: しきい値変更が根拠の数字と共にコミット済み。自分の Q3 の相関が出ている。別端末で初期状態から 5 分以内に最初の診断。
- **工数**: 5〜7 人日。

### フェーズ 2: 少人数ベータ(10 月下旬〜11 月下旬、4〜5 週間、PRD M5)
- **タスク**: 5〜10 人募集(D3)、初日観察(Q5)、毎週アンケートとエクスポート回収、不具合修正のみ(機能凍結、D8)、終了時インタビュー。
- **完了条件**: 5 人以上が 4 週間を終える。継続率・解決済みスレッド数・実感アンケートのベースライン。詰まった箇所と要望の上位 5 件。
- **工数**: 開発 週 1〜2 人日、運営 週 2〜3 時間。

### フェーズ 3: 精度とモデル(0〜2 と並行、11〜12 月)
- **タスク**: 自前の評価セット(MusicXML のあるフレーズを自分で弾いた 20〜30 本、楽譜お手本とアライメントして手直しした正解)。スマホで 3 秒超なら student-s か INT8 量子化(精度 1pt 以内か確認)。student-l は「スマホ 3 秒以内かつ自前評価で 2pt 以上の差」の場合のみ。生徒でストロークと 8 音/秒超を測り、SPEC 2 節を更新。
- **完了条件**: 自前評価セットでの両エンジンの F1、スマホ 3 秒以内のエンジンの決定、守備範囲表の更新。
- **工数**: 評価セット 3〜4 人日(録音は人間)、量子化等 2〜3 人日、学習 1 回 6〜8 時間。

### フェーズ 4: 機能拡張(12 月〜2027-02、ベータ結果で順序を決める)
1. C19 生の録音の聴き比べ
2. C12 解決済みの棚と再確認
3. C06 前回のつづき
4. C09 ハンズフリー録音(実機データで自動停止しきい値を詰める)
5. 週のふりかえり

入れない: C16 ボス戦、C14 バッジ、C10 テンポ階段。C04 カレンダーは保留。

### フェーズ 5: まとめ(PRD M6)
Goals ごとの判定、ベースライン、撤退と継続の判断、v2 PRD の要否。講座側の日程は未確認(終了は 2026-12〜2027-02 頃と推測)。**フェーズ 2 を最終報告の前に終えることを最優先**。

### 計測の方針(バックエンド無し、Non-goal と整合)
- 端末内 IndexedDB に `events` テーブル(開いた、録音した、診断を見た、エクスポートした、推論時間)。
- 「研究用エクスポート」で音声・音符列を含まない集計 JSON を作り、参加者が自分で送る。アプリは何も送信しない。
- 通知・リマインドは使わない。連絡はベータ運営(人間)が担う。

## 5. リスクと撤退基準

| リスク | 計測 | 撤退・切り替えの基準 |
|---|---|---|
| スマホで遅い・落ちる | Q1 | 生徒で 3 秒超なら student-s か量子化。どのエンジンでも 5 秒超ならテイク長を 15 秒に制限(推測の目安) |
| iOS で動かない(開発者は iOS 実機を持たない) | ベータ初日の参加者端末での確認 | 録音・再生・診断のどれかが通らなければ、iOS はベータ対象外とし参加者を Android に限る。修正は参加者の協力(画面録画・エラー文の共有)で進める |
| 指標のノイズがしきい値より大きい | Q2 | しきい値を 2 倍にしても同じ演奏で勝敗が付く割合が 30% 超なら、1 対 1 の勝敗をやめて「直近 3 本の中央値」との比較へ |
| 数字が実感と合わない | Q3 | 相関 0.2 未満なら勝敗表示を止めゲージのみに、聴き比べ(C19)を優先 |
| 継続しない | Q4 | 4 週目の週 1 回以上が 2 割未満で「価値が分からない」が多数なら、価値仮説を v2 PRD で見直す |
| iOS のストレージ自動削除 | 参加者の申告 | 既知リスクとして受け入れ、週 1 回のエクスポートを案内。2 件以上起きたら D2 を再議論 |
| ライセンス | 商用化の話が出たとき | GAPS 由来の重みを使わず再学習 |
| モデル改善の頭打ち | 自前評価セット | 学習 1 回あたり +1pt 未満が 2 回続いたら打ち切り |
| 手が足りない・期限 | 週次進捗 | フェーズ 3・4 を削ってもフェーズ 2 を最終報告前に終える |
| 被験者の偏り | 募集経路 | 「身内 n 人の値」と明記し一般化しない |

## 6. 直近 2 週間のタスク分担

### エージェントに任せられるもの
1. 録音 `mimeType` の実値化(`isTypeSupported`)
2. manifest アイコン(192 / 512、maskable)、スマホ幅 CSS、Vite `base`
3. ホスティング設定(Cloudflare Pages の `_headers` 等)とビルド手順
4. 段階別 ms 表示、端末内計測ログと JSON エクスポート(`events` テーブル)
5. 既定エンジン切替(フラグで戻せる形)と Basic Pitch の遅延読み込み(D1 決定後)
6. `comparison.ts`、`habit/verdict.ts`、`pickToday.ts` のユニットテスト
7. ノイズの底の集計スクリプト
8. SPEC の更新
9. 自己採点 UI(実験フラグ)、同意書・アンケート・案内文の下書き
10. 自前評価セット用フレーズ候補(MusicXML 8〜16 小節 × 5 種)と正解作成スクリプト

### 人間(開発者)にしかできないもの
1. D1〜D9 の決定(少なくとも D1、D2、D4、D5 は早めに)
2. Q1 の計測(手持ちの Android 端末。端末名・Android バージョン・Chrome バージョンを記録)
3. Q2 の録音(1 フレーズ × 1 日 10 テイク × 3 日)
4. 2 週間の毎日の使用と自己採点
5. 評価セット用フレーズの演奏・録音(20〜30 本)
6. ベータ参加者の打診(iPhone 利用者を 1〜2 人含め、iOS の確認役をお願いする)、講座側の日程確認
7. ホスティングのアカウント作成、組織リポジトリの公開範囲の確認
8. GAPS ライセンスの商用可否の確認(必要なら専門家)
