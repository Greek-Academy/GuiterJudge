# PRD: ギター楽譜照合診断アプリ（仮称）

**Status**: Draft v3 ｜ **Author**: (自分) ｜ **Date**: 2026-09-18（初版 2026-09-16）
**Context**: Alpha+プロジェクト（6ヶ月・ソロ推進）の中間地点で立てる、アプローチ転換版の別プロダクト
**関連**: 前身 [ギター上達診断アプリ PRD](../prd/guitar_diagnosis_prd.md) / [Design Doc Appendix A（楽譜インポート不採用の記録）](../prd/guitar_diagnosis_design_doc.md) / [現状仕様書](../../SPEC.md)

**v3 での変更点**: 楽譜の入口を MusicXML / Guitar Pro ファイルに限定し、PDF・紙の OMR 経路は「余裕があれば」に落とした。手元に紙しかない曲は練習区間だけ MuseScore で打ち込む前提を明記した。主な利用環境を PC のブラウザに置き直した。
**v2 での変更点**: 主な楽譜の出所を五線譜の PDF・紙に置き、OMR をアプリ外の事前工程にした（v3 で入口から外した）。構成を前身と同じ完全クライアントサイドに戻した。

## TL;DR
楽譜（MusicXML / Guitar Pro ファイル）を「正解」として取り込み、演奏を楽譜と照合して、**どの小節のどの音が、間違い・欠落・遅れ**なのかを音符単位で示す練習アプリ。前身が採った「過去の自分との比較」は、一貫性しか測れず正誤を判定できないという構造的限界があった。本プロダクトはその限界を、外部の正解データを持つことで根本から解消する。v1 は照合の価値を確かめることに集中し、紙や PDF からの取り込みは後回しにする。

## Problem / Background
- 独学のギタリストは、自分の演奏が楽譜通りに弾けているかを客観的に確認できない。「なんとなく弾けている気がする」まま同じ間違いを固定してしまう
- 練習している楽譜は市販の楽譜集（紙・PDF）が主で、アプリ内のライブラリに収まらない
- 前身（自己比較アプローチ）で実測して分かったこと
  - 自己比較は「一貫しているが間違っている」演奏を安定と診断し得る。お手本テイクを別に用意する回避策は、お手本を作る手間が本体の価値を上回った
  - 正解を知らない状態での音符起こし（Basic Pitch）は、ストローク和音を分解できず、16分音符級の速さで取りこぼす。「1音が2つに割れる」過剰検出も25%出た
  - メトロノーム格子による絶対的なタイミング指標は有効だった。ただし音高側に正解がないため、指標が「ズレ」を示しても「何と比べてのズレか」が弱い

## Why Not Existing Apps
| | Yousician / Rocksmith 系 | Soundslice / Guitar Pro / Songsterr | 本アプリ |
|---|---|---|---|
| 楽譜の出所 | アプリ内ライブラリ | ユーザーの楽譜を表示・再生 | ユーザーの楽譜ファイル |
| 演奏の判定 | あり（ライブラリ曲のみ） | なし（再生・練習補助のみ） | あり（取り込んだ楽譜なら何でも） |
| フィードバックの粒度 | ゲーム的な正解率 | — | 小節×音符単位の正誤とタイミング、履歴 |

既存ツールは「楽譜を持ち込む」と「演奏を判定する」のどちらか一方しか持たない。本アプリはその接続部を作る。

## Goals（v1で目指すこと）
1. **（核）** ユーザーが取り込んだ楽譜のどの小節・どの音が弾けていないかを、演奏直後に音符単位で確認できる
2. 小節範囲とテンポを指定した練習区間ごとに履歴を残し、テンポを上げながら弾けるようになっていく過程が見える

## Non-goals（v1ではやらない）
- **PDF・紙の楽譜の認識（OMR）**。ブラウザやスマホで動く実用的なライブラリがなく、既存ツールを使っても認識ミスの修正と周辺処理が v1 の規模を超える。紙しかない曲は練習区間だけ手で打ち込む。余裕があれば Audiveris / Opuscan を試す程度に留める（Appendix 参照）
- 手書き譜・タブ譜だけの画像の認識
- 弦・フレットの判定。判定は音高とタイミングのみ。運指が楽譜と違っても、鳴っている音が同じなら正解と扱う
- ベンド・ビブラート・スライド等のテクニック判定
- リアルタイム（演奏中）のフィードバック。v1 は録音 → 事後照合
- バックエンド・アカウント・外部サービス連携。前身と同じく完全クライアントサイドで、音声も楽譜も端末から出さない
- 曲ライブラリ、ソーシャル、通知・リマインド、ギター以外の楽器

## Target User / Persona
「島田さん（仮）、30代社会人、ギター歴3年、独学。市販の楽譜集（紙・PDF）の五線譜で練習している。
弾けているつもりの箇所が本当に楽譜通りか分からず、上達が頭打ちになっている。
練習は PC の前で行い、引っかかる数小節を MuseScore で打ち込む手間は許容できる」

## Key Scenarios
1. **楽譜ファイルを用意する**。MusicXML / Guitar Pro ファイルがある曲はそれを使う。紙しかない曲は、練習したい区間（数小節〜十数小節）だけを MuseScore 等で打ち込んで MusicXML に書き出す。曲全体を入力する必要はない
2. **アプリに取り込む**。ファイルを読み込むと楽譜として表示され、音を聴いて確認してから保存する。ギター譜の記譜オクターブは取り込み時に実音へ補正する
3. **練習区間を作る**。楽譜上で小節範囲を選び、テンポ（BPM）を決める。区間は楽譜1つに複数持てる。打ち込んだ楽譜が区間そのものなら全体を選ぶだけでよい
4. **録音する**。カウントインとクリック付きで区間を弾く。録音後、演奏が楽譜の音符と自動で対応付けられる
5. **結果を見る**。楽譜の上に音符ごとの正誤（一致・音高違い・欠落・余分）とタイミングのズレ（ms）が重なって表示される。小節ごとの集計で「どこが弱いか」がひと目で分かる
6. **積み重ねる**。同じ区間を繰り返すと、テンポ別・日付別の履歴が残る。指定テンポで一致率が安定したら区間を「クリア」にし、テンポを上げる
7. **曲通し**。楽譜ファイルが曲全体なら、区間を曲全体にして通常の照合がそのまま使える

## Solution / Approach
- **問題の置き換え**。正解の音符列が既知なので、演奏音声を「何の音か当てる」（盲目的な音符起こし）必要はなく、「期待した音がその時刻付近で鳴ったか」を照合すればよい。この置き換えが精度面の最大の武器で、和音も「期待するコードの構成音が鳴ったか」という検証可能な問いに変わる
- **照合エンジンは差し替え可能に作り、複数候補を並べて検証する**（前身は Basic Pitch 一択だった）
  - Basic Pitch（前身の資産。正解ありなら検出結果を期待音符に吸着させられるので、分割・取りこぼしの影響が減る見込み）
  - 単音向けピッチトラッカー（pYIN / CREPE 系）。単音フレーズは Basic Pitch より軽く安定する可能性
  - 楽譜側を合成音にして音声と直接 DTW で位置合わせする方式（クロマ / CQT 特徴）。和音に強く、音符起こしを介さない
  - 研究段階のギター専用モデル（TART 等）は候補として追跡するだけで v1 では使わない
- **楽譜データは MusicXML を正とする**（2026-08-15 の決定を踏襲）。表示・再生・カーソル同期・リピート展開は alphaTab（Guitar Pro と MusicXML の両方を読める）に任せ、自前で実装しない
- **入口はファイルに限定する**。取り込み口を MusicXML / Guitar Pro に絞ることで、OMR の精度・修正・オクターブ補正・声部の集合化といった周辺問題を v1 から切り離す。打ち込みに使う MuseScore は無料で、区間単位なら 10〜20 分で済む
- **構成**。前身と同じ完全クライアントサイドの PWA。**主な利用環境は PC のブラウザ**（楽譜ファイルと MuseScore が PC にあり、練習も PC の前で行うため）。Android Chrome でも動くようにするが、v1 では動作確認に留める。ストア配布が必要になれば Trusted Web Activity か Capacitor で既存コードを包む

## Success Metrics
- **技術（M-A で確定させる）**：意図的に仕込んだ誤り（音高違い・欠落・余分・遅れ）の検出率と誤警報率。合成音と実録音の両方で計測する。合成音基盤は前身から流用
- **取り込みの手間**：紙の楽譜から区間1つを打ち込んでアプリで使えるまでの時間。20 分を超え続けるなら入口の見直しが必要
- **利用**：区間の「クリア」数、同一区間でのテンポ上昇幅、週1回以上の練習ログ継続率（前身と同じくベースラインがないため目標値はユーザーテスト後に設定）
- **上達実感アンケート**（前身と同じ）

## Risks / Open Questions
- **手入力の手間が続くか**。区間ごとに MuseScore で打ち込む前提は、本人には許容できても他のユーザーには壁になり得る。v1 は本人が主なテストユーザーなので受け入れるが、入口を広げる（OMR 経路）判断は v1 の照合の価値が確認できてからにする
- **実録音での精度は前身でも未計測のまま**。本プロダクトでも M-A で必ず実録音を通す。合成音は実機より素直なので、合成音の数字だけで判断しない
- **ストローク和音**。「期待するコードが鳴ったか」への置き換えで扱える見込みだが未検証。扱えなければ v1 は単音・分散和音に絞る（前身と同じ守備範囲）
- **ギター譜のオクターブ慣習**。ギターの五線譜は実音より 1 オクターブ高く書くのが慣習で、MuseScore のギター譜テンプレートも同様。取り込み時の一律補正と、オクターブ違いを一致とみなす許容ルールが必要
- **多声部**。クラシック系の譜面は複数声部で書かれる。前身の照合は単旋律の音符列を前提にしていたので、声部をまとめた「同時に鳴るべき音の集合」への変換が要る
- **楽譜と演奏の意図的な差異**。リピートの省略、装飾音、オクターブ違いの運指などを「間違い」と出すと信用を失う。許容ルールとリピート展開の扱いを決める必要がある
- **音の分割（1音が2つに検出される）**。正解ありなら期待音符に吸着させて緩和できる仮説。M-A で確認する
- **残り期間**。Alpha+ の残り約3ヶ月で前身と本プロダクトの両方は進められない。本 PRD を採るなら、前身は中間発表の成果として凍結し、資産（録音・前処理・メトロノーム格子・アライメント・履歴 UI・デモデータ生成）を持ち越す
- 被験者が事実上自分1人に留まる問題は前身と同じ

## Rough Milestones（残り約3ヶ月を前提。6ヶ月枠を取り直す場合は M-B 以降を倍に伸ばす）
- **M-A: 技術検証（3週）**
  - MusicXML / Guitar Pro → 期待音符列（リピート展開・オクターブ補正・声部の集合化込み）の変換と alphaTab 表示
  - 自分が練習中の区間を 2〜3 個 MuseScore で打ち込み、所要時間を記録する
  - 照合エンジン候補（Basic Pitch 吸着 / 単音トラッカー / 合成音 DTW）を、前身の合成音基盤と自分の実録音で比較し、v1 のエンジンを決める
- **M-B: MVP（5週）**。ファイル取り込み → 区間作成 → クリック付き録音 → 音符単位の照合表示 → 履歴、の最小ループ
- **M-C: 調整（2週）**。許容ルール、オクターブ、声部など M-A・M-B で見えた詰まりどころへの対処。**余裕があれば** Appendix の OMR 経路を試す
- **M-D: 実機・ユーザーテストと成果まとめ（2週）**

## Appendix: 余裕があれば試す OMR 経路（v1 のスコープ外）
v2 で検討した内容の要約。着手する場合は、まず自分の楽譜 10〜20 ページを通して「修正なしで使えるページの割合」と「1 ページの修正時間」を測ってから判断する。

- **PC 経路（無料）**: PDF・スキャンは Audiveris（Java、`-batch -transcribe -export` でヘッドレス実行）、紙の写真は homr（Python、CPU 可）。修正は MuseScore
- **スマホ経路（有料）**: Opuscan（30 ページ約 $10、クラウド認識）か PlayScore 2（端末内認識、サブスクリプション）の Android アプリで MusicXML を書き出し、本アプリを Android の共有ターゲットにして受け取る。修正はそれらのアプリ内で行うため PC より手間
- **共通の壁**: OMR の到達点は研究水準でも記号誤り率が数十%（Sheet Music Benchmark）。ギター譜は五線とタブの併記、コードダイアグラム、指番号が誤認識源で、タブ譜単体は商用・OSS とも未対応。ブラウザ内で動く OMR ライブラリはなく、アプリ内蔵は選択肢に入らない
